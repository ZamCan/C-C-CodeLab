## Exam structure — binding design
- Support **up to 10 reviewed exam blueprints/variants per course or level** (not 10 questions); each exam attempt contains **exactly 25 top-level questions**. A course can have a larger versioned question bank. A learner gets one server-randomized variant/attempt, not all 10 at once. Blueprint version, topic coverage and difficulty must be auditable.
- Support 10 interaction/design families: (1) single/multiple choice, (2) true/false, (3) output prediction, (4) identify error, (5) fill in blanks/code completion, (6) rearrange code or statements, (7) debugging, (8) trace table, (9) algorithm/decision-table selection, (10) practical coding. Support subtypes and subparts within each family.
- **Question counting:** each top-level question counts **one of the 25**, regardless of its number of internal items. Example: reorder 7 statements = ONE question; a true/false question with 4 statements = ONE question; 3 related blanks inside one code fragment = ONE question. Do not incorrectly count each statement, blank or drag item as a separate question. Represent subparts in a structured `payload_json` and validate per family. Grade subparts under an explicit, published per-question rubric; never silently award extra questions. Permit weighted points across questions; total normalized to 100.
- Exam time is **short but defensible based on weight and complexity**, not a fixed arbitrary few minutes. Recommended initial configurable ranges: objective-only 25-question exam 20–30 minutes; mixed exams with ordering, multi-part questions and trace tables 30–45 minutes; real coding assessments 45–60+ minutes when isolated grading exists. Calculate/review blueprint duration using per-style expected effort and accommodations. Server controls start/deadline, not Android. Show countdown and autosave, resume after interruption without resetting deadline; support accessibility accommodations and documented outage appeals.
- Cryptographically secure selection, no leaked answer keys, minimum bank size, exposure avoidance and metrics. Do not promise mathematically impossible permanent 1% repeats with finite banks.
- Existing `policy.mjs` currently **restricts attempts to exactly two automatically graded styles**, `grade` assumes 25 equal 4-point single-choice answers, and D1 `attempt_questions` only stores `correct_index`. These are **known implementation gaps**; introduce versioned backward-compatible migrations and tests before enabling richer formats. Do not activate `practical_coding` without isolated sandbox grader and hidden tests; Workers orchestrate only.
